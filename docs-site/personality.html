Conversational behavior configuration

The runtime source of truth is bridge_config.py:BASE_SYSTEM_PROMPT. The compatibility facade in bridge.py re-exports that value for existing imports.

This public page intentionally does not reproduce the prompt text, its section ordering, identity strings, internal operator phrasing, tool-routing instructions, or behavioral enforcement grammar. Those details are implementation configuration, not a public integration contract.

Public behavior contract

  • Wait for the user to speak before producing first-turn audio.
  • Answer directly and keep spoken responses structured.
  • Use tools only through the configured runtime boundary.
  • Describe video or screen content only when an authenticated frame was received for the current interaction.
  • Keep vocal-expression markup bounded.
  • Do not treat personality wording as authorization to bypass security, privacy, confirmation, identity, or tool-permission controls.

Prompt wording alone does not prove that a capability works. The bundled frame paths remain blocked on current main; see Issue #9.

Editing the configuration

Edit BASE_SYSTEM_PROMPT in bridge_config.py, not only the bridge.py compatibility facade.

  1. Compile-check both files: python -m py_compile bridge_config.py bridge.py.
  2. Restart the gateway: systemctl --user restart hermes-gateway.
  3. Test the affected behavior in a controlled voice session.
  4. Re-check that executable policy still owns security, privacy, identity, confirmation, and permission boundaries.

Dynamic context

Per-session Honcho context may supplement the static prompt. It is controlled by VOICE_LIVE_HONCHO_CONTEXT; HONCHO_CONTEXT_ENABLED is the corresponding Python constant. VOICE_LIVE_HONCHO_MAX_CHARS limits the appended context size.

Dynamic context may contain user-specific or session-specific material. Do not copy live context payloads, profile conclusions, identifiers, or private session content into public documentation, issues, logs, or examples.

Public documentation boundary

Public docs may explain observable behavior, supported configuration names, validation steps, and known limitations. They should not publish verbatim system prompts, detailed control-language maps, privileged routing or mutation instructions, embedded user identities, or secret and tool-authorization grammar.
