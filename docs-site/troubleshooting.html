Troubleshooting

Use this page with the current repository issues. Several advertised paths remain intentionally documented as blocked or limited until their runtime and security fixes are reviewed on an exact commit.

/voice-live cannot infer a safe voice channel

Set DISCORD_VOICE_LIVE_USER_ID explicitly, or supply both guild_id and channel_id from a trusted caller. Current runtime otherwise retains a deployment-specific fallback that is unsafe for reused or multi-user installations. See Issue #16.

grep '^DISCORD_VOICE_LIVE_USER_ID=' "${HERMES_HOME:-$HOME/.hermes}/.env"

Bridge seems slow to start

Let one connection cycle finish. Repeated gateway restarts reset retries and can worsen rate limiting.

journalctl --user -u hermes-gateway -f

Useful log markers include VoiceLive: connecting, the loopback control listener, Gemini setup completion, and VoiceLive: bridge active. Do not rely on fixed retry counts or timing as a compatibility guarantee.

Health check says not started

curl -s http://127.0.0.1:18943/health | python3 -m json.tool

If the sidecar is unavailable, the bridge is not running or the configured port differs. A not_started response means the HTTP server is reachable but no active bridge object is registered.

Mutating sidecar routes are blocked on current main

Authentication for /stop, /say, /frame, and /notify currently fails before a controlled authorization response. Do not use or expose those routes while Issue #5 remains open.

/health is anonymous. /notes is also unauthenticated and returns private transcript events plus the backing notes-file path. Keep the sidecar bound to loopback; do not proxy or browser-expose it while the privacy and control-API findings in Issue #4 remain open.

Video frames are not delivered

Frame delivery is blocked by the sidecar authentication defect, missing client authentication headers, feeder argument parsing, and secret-file-path mismatches. Treat the feature as unavailable until Issue #9 is resolved and exact-head tests cover both built-in and external clients.

Gemini setup fails for every model

Check the API key, selected model, and fallback list without printing secret values:

grep -E '^(GEMINI_API_KEY|GOOGLE_API_KEY|GEMINI_MODEL|GEMINI_LIVE_MODEL_FALLBACKS)=' "${HERMES_HOME:-$HOME/.hermes}/.env"
journalctl --user -u hermes-gateway -n 100 --no-pager | grep -i 'Gemini Live model\|Gemini connect failed\|setup'

No inbound audio reaches Gemini

Inspect /health for an active voice connection, receiving state, decoded-frame counters, and increasing input chunks while speaking. Common causes include a missing receive extension, speaker filtering, bot-speaker filtering, or speech below the local energy gate.

Audio output is late or talks over the user

Check interruption and output-buffer settings in Environment variables. Review health counters and logs before changing multiple timing values at once. Audio-path changes are runtime-sensitive and require normal review.

Tool calls hang

Blocking handlers can queue later calls. Inspect the gateway journal for the specific tool and avoid assuming that a submitted external task completed successfully merely because the bridge accepted the request.

journalctl --user -u hermes-gateway -n 100 --no-pager | grep -i 'tool call\|local_\|opencode_'

Fallback selection is not portable

The current fallback implementation contains host-specific executable paths, and suggestion-time and execution-time eligibility checks are not fully aligned. Do not edit source paths as routine setup guidance. See Fallback chain and Issue #8.

Email brief looks empty after backend failure

Current backend failure can be represented like a successful empty inbox. Delivery failures can also produce misleading notification and de-duplication state, and recipient fallback can route sensitive sender or subject data incorrectly. Do not treat an empty brief as proof of backend health; keep scheduled delivery disabled until the destination and privacy boundary are verified. See Email brief and Issue #10.

Notification was not delivered

The built-in /notify client does not currently satisfy the sidecar authentication boundary. Scheduled notification state also remains under $HOME/.hermes rather than following a custom HERMES_HOME. See Notifications, Issue #5, and Issue #20.

Custom HERMES_HOME still writes elsewhere

Some runtime state does not yet follow the installation root. SFX paths, scheduled notification state, and the Google Workspace helper lookup have separate open corrections in Issue #18, Issue #20, and Issue #21. Do not move or delete legacy state until both old and new locations are inspected.

Installer rerun or unattended setup is misleading

A normal rerun is not a verified update, and --no-prompt does not provide a complete deterministic install contract on current main. The interactive credential writer can also corrupt some special-character values. Back up local changes and inspect the target before using --from-local. See Quick start, Issue #11, and Issue #23.

SFX is missing or silent

Confirm the configured SFX directory and active voice session. A custom HERMES_HOME does not yet relocate SFX consistently, and bundled clip redistribution rights remain unverified. See SFX library, SFX credits, Issue #18, and Issue #12.

Log and private-data locations

  • Gateway: journalctl --user -u hermes-gateway -f
  • Hermes logs: ${HERMES_HOME:-$HOME/.hermes}/logs/
  • Bridge notes/transcripts: $HOME/.hermes/voice-live-notes/ by current default; treat as private conversation data
  • Scheduled notifications: $HOME/.hermes/voice-scheduled-notifications.jsonl on current main
  • SFX: $HOME/.hermes/voice-users/sfx/ on current main
  • Control secret: $HOME/.hermes/voice-live-control-secret by runtime default
